0. 사용자 목적과 실행 범위
======================================================================

내 목적은 로컬 GPU에서 서로 다른 여러 모델을 의료 데이터로 파인튜닝하고,
각 모델의 학습 전후 차이와 모델 계열 간 차이를 재현 가능한 조건에서 알아보는 것이다.

이번 V6에서 다음 질문에 답하라.
- 같은 의료 학습 표본을 주었을 때 어떤 모델이 한국어 의료 문항에 더 잘 답하는가?
- 개선이 내용 정답의 증가인지, 답변 형식 준수의 증가인지, 둘 다인지?
- 한국어 학습 후 영어 의료 질의응답 성능은 어떻게 달라지는가?
- 일반 Gemma와 의료 특화 MedGemma를 추가 학습하면 어떤 차이가 생기는가?
- 의료 이미지 QA에서 단답형과 자유응답형, 학습 데이터와 다른 평가 데이터의 결과가 어떻게 다른가?
- 정확도·응답 형식·추론 시간·메모리·학습 비용을 함께 보면 어떤 용도에 어떤 모델이 적합한가?

분석이나 계획 파일 작성으로 끝내지 말고, 아래 유한한 행렬의 구현·실제 학습·평가·보고까지 진행하라.
장시간 GPU 학습은 채팅 턴과 독립된 worker로 실행한다. 초기 구현과 등록 검증을 마치면
채팅 턴을 끝내고 예약 점검으로 이어간다. 학습이 끝날 때까지 대기·polling을 반복하며 한 턴을 붙잡지 않는다.
기존 사용자 승인에 따라 로컬 환경 안의 통상적인 설치, 코드 수정, 공개 모델 확보, 학습,
평가, 결과 정리, 작업 브랜치 commit/push를 반복 확인 없이 진행하라.
도구의 실제 접근 제약이나 승인 절차를 우회하지는 않는다.

GPU 누적 시간 상한은 없다. total/model/run/job/campaign 시간 상한을 다시 만들지 말라.
다만 선언된 모델·데이터·seed·1 pass로 작업 범위를 고정한다.
시간이 남았거나 점수가 낮다는 이유로 모델·데이터·epoch·seed를 계속 늘리지 않는다.

Jetson 실행·접속·배포는 이번 범위에서 제외한다.
현재 로컬 학습 장비와 데이터 경로를 사용하고, 유료 cloud GPU·유료 API 호출을 새 필수 조건으로 만들지 않는다.
이 프로젝트의 비교를 끝내기 위해 kiosk/dashboard/server 배포를 선행 과제로 추가하지 않는다.
main 병합은 하지 않는다. 현재 학습·데이터·사용자 변경과 기존 Release를 보존한다.

2. 비교 모델과 실행 행렬을 고정하라

텍스트 의료 QA: 6개 모델/작업 셀
T1  Qwen/Qwen3-1.7B                 family=qwen       역할=작은 모델/기존 기준
T2  Qwen/Qwen3-4B                   family=qwen       역할=크기 통제/기존 기준
T3  google/gemma-3-4b-it            family=gemma      역할=일반 Gemma
T4  google/medgemma-1.5-4b-it        family=gemma      역할=의료 특화, 새 text SFT
T5  microsoft/Phi-4-mini-instruct   family=phi        역할=다른 계열, 약 3.8B
T6  HuggingFaceTB/SmolLM3-3B        family=smollm     역할=다른 계열, 3B

이미지 의료 VQA: 4개 모델/작업 셀
V1  Qwen/Qwen3.5-2B                       family=qwen_vlm
V2  google/gemma-3-4b-it                  family=gemma_vlm
V3  google/medgemma-1.5-4b-it              family=gemma_vlm
V4  HuggingFaceTB/SmolVLM2-2.2B-Instruct   family=smolvlm

총 8개 고유 model ID, 10개 model×task 셀이다.
Gemma/MedGemma의 text adapter와 VQA adapter는 반드시 별도이며 각 원본 모델에서 독립 학습한다.
MedGemma VQA adapter를 text 의료 SFT 결과로 세지 않는다.
여기서 Base는 우리가 의료 SFT를 하기 전의 지정된 공개 체크포인트를 뜻한다.
모든 Base가 사전학습만 된 raw base라는 뜻은 아니다.

각 셀의 1차 비교는 Base vs 공통 데이터로 SFT한 모델 1개다.
처음부터 EN/KO/MIX/71762 등 모든 데이터 조합을 모든 모델에 곱하지 않는다.

공식 카드상 Phi-4-mini는 한국어 지원을 명시한다.
SmolLM3의 주요 지원 언어 목록에는 한국어가 없으므로 한국어 결과는 추가 학습 전이 탐색으로 해석한다.
SmolVLM2의 text decoder는 SmolLM2 계열이다. SmolLM3와 같은 decoder라고 쓰지 말라.
Gemma와 MedGemma 비교는 실용적 체크포인트 차이를 보여주지만
모든 사전학습·vision encoder·후속 학습이 같다는 인과 실험은 아니다.

새 모델마다 공식 카드·라이선스·현재 native 지원을 확인하고 weight revision SHA를 고정한다.
모델 이름만 고정하거나 floating main revision으로 여러 실행을 섞지 않는다.
이미 확인된 Gemma/MedGemma 접근권과 로컬 credential을 재사용한다.
실제 401/403·credential 만료가 없는데 접근 승인이나 API 키 제출을 다시 요구하지 않는다.

이번 기본 행렬에는 예비 모델을 추가하지 않는다.
특정 후보가 제한된 기술 복구 후 실패하면 그 셀과 관련 seed를 명시적 실패/차단 상태로 남기고
다른 모델은 계속한다. 임의로 더 작은 모델로 바꾸어 같은 비교 행을 채우지 않는다.
교체 후보 제안은 최종 보고에 남길 수 있지만, 새 모델을 계속 탐색하며 작업을 연장하지 않는다.

3. 장비·모델 로더·LoRA 지원을 실제 실행으로 검증하라
======================================================================

현재 GPU·VRAM·CUDA·PyTorch·Transformers·PEFT·bitsandbytes·드라이버 상태를 기록한다.
기존 기록의 RTX 3060 12GB를 현재 장비라고 가정하지 않는다.
nvidia-smi/NVML 오류만으로 GPU가 없다고 결론내리지 말고 실제 CUDA 연산을 확인한다.
신규 모델의 12GB 학습 가능 여부는 아직 검증되지 않았다.

의존성 변경이 기존 성공 환경과 충돌하면 V6 전용 가상환경을 만든다.
기존 학습 환경과 source snapshot을 덮어쓰거나 OS/드라이버를 교체하지 않는다.

각 새로운 model×task 경로에서 다음을 통과시킨다.
- config의 native architecture와 공식 tokenizer/processor/chat template 확인.
- 기본적으로 native implementation과 trust_remote_code=False 사용.
  필요한 외부 코드는 출처·revision·실행 내용을 검토해 현재 허용 범위에서 처리한다.
- 텍스트 경로에는 image/pixel tensor가 없고, VQA 경로에는 실제 이미지가 들어가는지 확인.
- native template의 assistant prefix, padding/image token, loss mask 확인.
- 정답 token만 학습하는지 확인하고 prompt/image/pad token에 loss가 걸리지 않게 한다.
- 실제 CUDA forward/backward, finite loss/gradient, optimizer update,
  adapter weight 변화, 저장, 새 process reload를 확인한다.
- model×task별 20 optimizer-update smoke를 사용하되 train partition에서만 표본을 취한다.
  이 smoke adapter를 본학습 시작점으로 사용하지 않는다.
- 동일 경로의 추가 seed는 이미 검증한 smoke를 중복 실행하지 않아도 된다.

LoRA의 주 비교 규약:
- 언어 decoder block 내부 attention 및 MLP의 선형 projection에 적용한다.
- embeddings, 최종 lm_head, vision encoder, multimodal projector는 제외·동결한다.
- 모델별 실제 named_modules에 근거해 대응 범위를 정한다.
  Qwen용 q_proj/k_proj/v_proj 등의 suffix 목록을 모든 계열에 그대로 복제하지 않는다.
- Phi의 fused QKV/gate-up, Qwen3.5의 hybrid/linear attention 등 구조 차이를 반영한다.
- 실제 대상 경로 전체, module 종류별 커버리지, 전체/언어/vision/학습 parameter 수,
  adapter 변화·gradient 확인 결과를 남긴다.
- 대상 모듈이 한 개라도 발견됐다는 사실만으로 올바른 LoRA 지원이라고 판정하지 않는다.

특히 기존 Qwen3.5 VQA의 96개 대상은 MLP와 일부 full self-attention projection이며
linear_attention 모듈이 포함되지 않았다. V6에서 대상 범위를 확장하면
기존 adapter는 같은 학습 처방이 아니므로 해당 셀을 새로 학습한다.
재사용 수를 늘리려고 신규 모델의 LoRA 검증 기준을 낮추지 않는다.

모델별 공식 방법으로 thinking을 끈 주 비교를 준비한다.
enable_thinking=False를 넘겼다는 사실만으로 모든 모델에서 비활성화됐다고 간주하지 않는다.
실제 렌더링과 출력으로 확인한다. 같은 조건을 구현할 수 없는 모델은 차이를 명시하고,
숨겨진 reasoning 비용이나 다른 출력을 동일 조건으로 주장하지 않는다.

한 GPU에 하나의 학습/평가 worker를 사용한다.
OOM은 gradient checkpointing, 검증된 attention backend, 불필요 tensor 해제 등으로
제한적으로 복구하되 모델 하나만 데이터/epoch/정답 길이를 몰래 줄이지 않는다.
모델·단계별 기술 복구는 최초 시도 이후 최대 2회로 제한하고 오류 원인을 보존한다.
기술적으로 불가능한 셀 때문에 전체 비교를 중단하지 않는다.

======================================================================
4. 같은 데이터가 실제로 같은 학습 표본이 되도록 동결하라
======================================================================

텍스트 주 학습 후보는 기존 v2 MIX 8,000개:
- AIHub 71875 4,000개
  (기존 구성: 객관식 1,500 / 단답 1,300 / 서술 1,200)
- MedQuAD 3,550개
- PubMedQA 450개

공통 validation 후보는 기존 1,516개:
- AIHub 71875 758개
- MedQuAD 708개
- PubMedQA 50개
최종 758개의 q_type별 수는 실제 frozen 파일에서 다시 집계한다.
격리 전 956개의 q_type 집계를 그대로 적용하지 않는다.

VQA 주 학습 후보는 기존 SLAKE train 1,979개,
validation은 512개, test는 1,061개다.
VQA-RAD 451개는 외부 평가로 보존하고 학습/모델 선택에 사용하지 않는다.

모든 후보 tokenizer/processor를 본학습 전에 검사한다.
train은 학습 context 2,048 기준으로 실제 native input+target 길이, 이미지 처리, 정답 보존,
마스킹, source/task/label별 제외 사유를 확인한다.
지원 가능한 모델들이 모두 처리할 수 있는 공통 train sample IDs를 축별로 동결한다.
dev/test의 처리 가능성은 별도의 평가 context와 입력만으로 확인한다.
정답의 길이 또는 내용·난이도로 평가문항을 고르지 않는다.
어떤 모델만 초과 길이 표본을 조용히 버리고 동일 데이터 비교라고 하지 않는다.

공통 교집합이 달라지면 새 V6 freeze를 만든다.
train/dev/test의 기존 split과 group 경계를 유지하고 전체를 다시 섞어 분할하지 않는다.
학습 본문이나 정답을 잘라 형식만 맞추거나 누락 표본을 다른 질문으로 대체하지 않는다.
원래 수량→모델별 eligible 수량→최종 공통 수량을 source/language/task별로 공개한다.
데이터가 줄면 대표성의 변화도 기록한다. 완료한 다른 모델에 맞추어 사후 재추첨하지 않는다.
preflight/smoke 이후 비교 대상과 공통 train 집합을 한 번 동결한다.
이후 어떤 셀이 실패해도 교집합을 넓히거나 완료된 모델의 데이터·평가 분모를 다시 만들지 않는다.

학습은 같은 예제·같은 순서 규칙·같은 pass 수로 맞춘다.
토크나이저가 다른 모델의 실제 token 수까지 같다고 주장하지 말고 input/target token을 측정한다.
seed를 바꿀 때는 데이터 구성과 split을 유지하고 학습 순서·초기 LoRA 등의 난수만 바꾼다.

재사용할 데이터 감사:
- KorMedMCQA dev 1,059 + test 3,009 전체 4,068개를 학습 오염 보호 대상으로 유지.
- 71875의 test는 공식 Validation에서 파생한 평가분이다. 독립 공식 Test라고 부르지 않는다.
- MedQuAD의 원문 문서/URL 그룹, PubMedQA의 PMID/fold를 유지.
- SLAKE의 원본 이미지·decoded pixel·perceptual duplicate group 경계를 유지.
- 기존 감사에서 발견한 semantic 후보를 확정 중복 또는 완전한 오염 제거라고 표현하지 않는다.
- 새로운 데이터 변경에 필요한 감사만 추가한다.
  이미 완료한 원본 수집·전체 압축 감사·HWP 추출을 이유 없이 다시 수행하지 않는다.
- VQA의 이미지 그룹 독립성을 환자/연구 단위 독립성으로 확대 해석하지 않는다.

V6의 주 학습에는 71762를 포함하지 않는다.
MedMCQA도 이번 주 학습에는 추가하지 않는다.
기존 준비된 MedMCQA dev 2,816개는 선택 지표와 분리된 추가 평가 후보로만 둔다.
이를 사용할 경우 모든 사용 train 및 모델 선택/calibration에 사용한 validation과의
exact/near/semantic 및 번역 유사성 후보를 감사한다.
후보 처리 방식, 동일한 평가 cohort와 최종 분모를 V6 test 추론 전에 고정한다.
겹침·노출 후보를 남긴 경우 독립 외부 평가로 주장하지 않는다.
해당 추가 평가를 사용할 수 없으면 이유를 기록하고 주 행렬은 계속한다.
정답 없는 MedMCQA 공식 test 6,150개에 임의 정답을 붙여 채점하지 않는다.

======================================================================
5. 학습 처방, final checkpoint, 기존 결과 재사용
======================================================================

텍스트 축의 공통 learning rate: 2e-4
VLM 축의 공통 learning rate: 1e-4
두 축을 서로 같은 학습 task나 같은 데이터 양의 실험이라고 비교하지 않는다.

공통 기본 처방:
- NF4 4bit + double quant, 실제 지원 시 BF16.
- LoRA r=8, alpha=16, dropout=0.05.
- microbatch=1, gradient accumulation=16, 유효 batch=16.
- train max_length=2048, gradient checkpointing 활성화.
- AdamW, weight_decay=0, linear decay, warmup=0, gradient clip norm=1.0.
- betas/eps 등 생략됐던 값은 기존 실제 환경/optimizer 기록을 확인해 V6에 명시.
- loss는 기존처럼 각 예제 안의 target-token 평균을 구한 뒤 예제 평균을 취한다.
  token 수에 비례해 예제 가중치를 바꾸는 목적함수로 몰래 변경하지 않는다.
- 첫 seed=20261023.
- 본학습은 고정 train을 1 pass.
  원래 전체 수량을 유지하면 text 500 updates, VQA 124 updates가 기준이다.
  마지막 미완성 batch의 처리와 예제 수를 명시하고 끝부분을 반복 채우지 않는다.
- 주 비교 checkpoint는 1 pass의 최종 checkpoint.
  중간 checkpoint와 validation은 진행·오류 진단용으로 보존한다.
  모델마다 서로 다른 노출량의 best-loss checkpoint를 섞어 주 표를 만들지 않는다.

기존 runner/reload의 selection.json은 minimum-validation-loss checkpoint를 가리킬 수 있다.
기존 selection.json은 변경하지 말고 V6 final_checkpoint receipt를 별도로 만든다.
정상 완료, 공통 train 전량의 1 pass 처리, ceil(N/16) updates를 확인한 checkpoint만 final로 인정한다.
중단된 run의 latest를 final로 간주하지 않는다. reload와 평가가 실제 final을 사용했는지 검증한다.

저메모리 설정을 바꿔야 하면 학습 전에 규약에 기록한다.
동일한 rank가 동일 trainable parameter 수나 동일 FLOPs를 뜻하지 않는다는 점을 보고한다.
이번 결과는 공통 처방 아래의 비교이며 각 모델별 최대 잠재 성능을 찾은 결과는 아니다.

각 셀에 대해 reuse receipt를 작성한다.
- 학습 재사용: base revision, 실제 train IDs/내용/순서, token rendering/마스킹,
  실제 학습 관련 코드, LoRA 범위, optimizer/학습률/목적함수/seed/pass가 같아야 한다.
- 평가 재사용: 위 조건에 추가해 선택 checkpoint, evaluation IDs, native prompt,
  processor, decoding, 길이, parser/scorer가 같아야 한다.
- 저장 경로·보고서 이름·GPU 시간 정책의 차이는 학습 처방 차이와 구별한다.
- training이 같아도 V6 평가 규약이 달라지면 새 예측을 생성한다.
- 기존 config/hash/run ID를 편집해 재사용 조건을 맞추지 않는다.
- 코드가 바뀌어도 training에 영향 없는 변경이면 근거를 기록해 기존 adapter를 연결할 수 있다.
- 조건이 다르면 새 run ID로 학습한다. 기존 결과는 역사 참고표로 보존한다.

기존 재사용 후보:
- Qwen3-1.7B/4B의 v2 MIX 최종 step 500.
- MedGemma VQA 최종 step 124.
- Qwen3.5 VQA의 기존 선택은 step 100이지만 최종 step 124도 보존되어 있다.
  단, V6 LoRA 범위를 확장하면 이 adapter는 동일 처방 재사용 대상이 아니다.

새 text/VQA adapter는 항상 지정 Base에서 시작한다.
이전 EN→KO→MIX 또는 VQA→text adapter를 연속 학습해 독립 비교라고 하지 않는다.
모든 성공 본학습은 새 process에서 checkpoint reload와 실제 추론을 검증한다.

======================================================================
6. 형식과 내용, 언어와 작업 유형을 분리해 평가하라
======================================================================

V6 protocol을 본 test 추론 전에 고정하고 version/hash를 남긴다.
동일한 의미의 과제 지시와 label 집합을 native chat template에 맞게 적용한다.
모델마다 더 유리한 지시·few-shot 예제·parser를 사후 선택하지 않는다.

생성 규약:
- greedy, sampling 비활성화, 주 비교에서 thinking 비활성화.
- 우선 MCQ/분류형 max_new_tokens=64, 자유서술/VQA=256을 사용한다.
- train과 eval의 context 제한은 별도다. 기존 text eval의 4096과 train 2048을 혼동하지 않는다.
  eval context는 4096을 시작점으로 입력 전체와 생성 여유를 모든 모델에서 사전 점검한다.
- 고정 validation calibration subset에서만 길이/메모리의 기술적 적합성을 확인한다.
- 길이 제한 때문에 종료된 비율이 task별 1%를 넘는 모델이 있으면 해당 task의 모든 모델에 한 번만
  MCQ/분류형 64→128, 자유서술/VQA 256→512로 동일 상향한다.
  상향 후 남는 잘림은 그대로 보고한다.
- 첫 seed 본학습 완료 후 원본 Base와 첫 seed Tuned의 validation으로 이 결정을 끝낸다.
  cap 변경 시 관련 validation을 동일 설정으로 다시 생성한 뒤 모델을 선택한다.
  이 상한은 추가 seed에서도 유지하며 재선택하지 않는다.
- 출력 길이 또는 내용 점수가 마음에 들지 않는다는 이유로 test를 본 뒤 재보정하지 않는다.
- context 초과 입력을 모델별로 조용히 잘라 비교하지 않는다.
  dev/test의 예정 문항은 전체 유지하고 입력 처리 불가도 기술 실패로 분모에 포함한다.
  필요하면 모든 모델이 처리 가능한 공통 subset의 보조 표를 추가하되 전체 표를 대체하지 않는다.

텍스트 주 평가는 기존 공통 4,530문항을 기준으로 한다.
- KorMedMCQA 3,009
- AIHub 71875 객관식 777 / 단답 83 / 서술 97
- PubMedQA 500
- MedQuAD 64
입력 처리 불가나 누락이 있으면 전체 예정 분모·성공 수·실패 수를 함께 기록한다.
이미 본 v1/v2 benchmark를 새 blind test라고 부르지 않는다.

분류형에는 다음을 각각 보고한다.
1) strict all-row accuracy: 형식 무효·미응답을 포함한 전체 분모의 정답률
2) valid-format rate
3) answered accuracy: 유효 형식 응답 중 정답률, 실제 분모 포함
4) invalid/abstention/technical failure/truncation 각각의 비율
5) Base→Tuned의 correct/incorrect 및 valid/invalid 전환 수

추가로 선택지 likelihood 점수를 별도 지표로 구현한다.
- 같은 질문·선택지를 보고 가능한 정답 label의 전체 token sequence에 대한
  conditional log-likelihood를 계산해 선택한다.
- 첫 token만 읽거나 생성 답변에서 정답처럼 보이는 글자를 임의 추출하지 않는다.
- native assistant prefix와 BPE 경계를 검증하고 정답을 prompt로 누출하지 않는다.
- 모든 label token의 합을 사용하며 EOS 포함 여부는 동일하게 고정한다.
- label 목록/순서/점수/선택을 저장한다.
- 이 값은 자유 생성 strict 점수를 대체하지 않는다.
  생성 형식의 영향을 줄여 보는 보조 결과이며 임상 능력의 순수 측정이라고 하지 않는다.
- 이 추가 scorer 실패가 성공한 생성 평가를 무효화하지 않게 별도 상태를 관리한다.

자유서술은 기존 exact/normalized EM·lexical F1과 길이/잘림을 보고한다.
숫자·단위·부정 표현을 지워 점수를 높이지 않는다.
문자열 유사도를 임상적 정답률이라고 쓰지 않는다.

VQA:
- SLAKE test 1,061 및 VQA-RAD 451의 같은 이미지/질문 IDs를 사용.
- Base/Tuned, OPEN/CLOSED, source별 normalized EM·F1을 별도 보고.
- 원래 answer_type 같은 채점 metadata를 모델 입력에 노출하지 않는다.
- 모델별 native processor의 해상도/crops/tiles/시각 token 수를 기록.
- 영상 encoder/projector 동결, 실제 pixel tensor 입력을 확인.
- 고정된 32개 진단 사례에 같은 모델의 이미지 있음/없음 비교를 수행.
  정상적으로 지원되는 no-image 경로가 없으면 진단 불가를 기록한다.
- MedGemma의 SLAKE dataset-level 사전학습 노출 및 정확 test 노출 미상 한계를 유지.
- 영어 VQA 점수를 한국어 이미지 질의응답 성능으로 해석하지 않는다.
  이번 행렬을 위해 자동 번역한 의료 VQA를 전문가 검증 데이터로 만들지 않는다.

사람 검토:
- 기존 rubric을 활용해 모델별 같은 문항을 보는 익명 검토 패킷을 준비한다.
- 모델 정체/A-B key와 원문은 private로 보존한다.
- 검토 미실행이면 0건으로 표기하고 점수 칸을 채우지 않는다.
- human review 완료를 이번 자동 비교의 선행 차단 조건으로 만들지 않는다.

======================================================================
7. 추가 seed는 validation으로 고른 다른 계열에만 수행하라
======================================================================

1차 10셀의 seed 20261023 결과를 같은 protocol의 전체 공통 validation에서 평가한다.
기존 text 48개 loss 또는 VQA 32개 출력 길이 검사는 이 모델 선택을 대신하지 못한다.

텍스트 선택용 연구 지표:
K = mean(71875 MCQ strict accuracy, 71875 short lexical F1, 71875 long lexical F1)
E = mean(PubMedQA strict accuracy, MedQuAD lexical F1)
S_text = 0.5*K + 0.5*E

VLM 선택용 연구 지표:
S_vlm = 0.5*(SLAKE dev OPEN normalized EM + SLAKE dev CLOSED normalized EM)

전체 공통 dev에서 해당 stratum의 모든 예정 문항을 분모로 쓴다.
실제 stratum 수와 각 구성 점수를 공개한다.
이 합성 지표는 추가 seed 투자 대상을 고르는 연구용 규칙이며 임상 정확도가 아니다.
기술적으로 미완료인 모델은 정상 완료 후보와 동일하게 취급하지 않는다.

Tuned의 절대 validation 지표로 각 family 안의 대표 1개를 먼저 정하고,
대표들 중 상위 2개 서로 다른 family를 축별로 고른다.
Qwen 두 크기를 다른 family로 세거나 Gemma와 MedGemma 둘만 선택해 두 계열이라고 하지 않는다.
동점은 반올림 전 분류형 점수 평균(텍스트) 또는 전체 EM(VLM),
그 다음 사전 선언한 model ID 사전순으로 결정한다.
Base 대비 증가량이나 test 점수로 추가 seed 대상을 고르지 않는다.

선정 모델·validation IDs·protocol·점수·선택 코드 hash를 selection receipt에 동결한 후
seed 20261114와 20261115로 각 대표를 Base에서 새로 학습한다.
데이터와 학습 처방은 그대로 유지한다.
선정 코드는 test metrics 경로를 읽지 않게 한다.
모든 1차 모델의 공통 validation과 family/추가 seed 대상 receipt가 확정되기 전에는
어떤 V6 test 추론·채점도 실행하지 않는다. 확정 뒤에는 test 결과로 선정 대상을 바꾸지 않는다.

전체 실행 순서는 다음과 같다.
preflight/smoke → 데이터·처방 동결 → 첫 seed 본학습 → validation 길이 규약 동결
→ 전체 dev 평가 → family/추가 seed 대상 동결 → 추가 seed 학습 → test 평가·보고.

계획 수량:
- 1차 10개 model×task×seed 조건.
- text 2가족 + VLM 2가족에 각 추가 seed 2개 = 추가 최대 8조건.
- 총 최대 18개 본학습 조건. 동일 조건의 검증된 역사 adapter 재사용은 실제 신규 학습을 줄인다.
- smoke·복구 시도·Base 추론은 본학습 조건 수와 구별한다.
- 일부 셀 실패로 해당 family가 성립하지 않으면 가능한 다른 family에서 규칙대로 선택한다.
  다른 family가 2개 미만이면 가능한 만큼만 실행하고 부족 사유를 남긴다.
- 추가 seed 실패 시 다른 모델을 test 결과로 다시 골라 대체하지 않는다.

모든 모델을 같은 1개 seed로 비교하는 주 표와,
선정된 모델만 3개 seed로 비교하는 확인 표를 분리한다.
1개 seed 결과와 3개 seed 평균을 한 순위에 섞어 동등하게 비교하지 않는다.
추가 seed에서 가장 좋은 checkpoint/seed만 골라 보고하지 않는다.
3개 seed 모두의 결과, 평균·표준편차·범위를 남긴다.

======================================================================
8. 속도·메모리·학습 비용을 같은 장비에서 측정하라
======================================================================

동일 GPU, batch 1, task별 고정 입력 subset, 고정 decoding,
일정 warmup 후의 반복 측정으로 비교한다.
GPU 동기화를 반영한 wall time을 사용한다.

다음 값을 모델·task·Base/Tuned별로 남긴다.
- end-to-end latency p50/p95와 표본 수
- 실제 측정 가능한 경우 TTFT 및 decode 시간; 측정하지 못하면 미측정으로 표기
- peak allocated/reserved VRAM, 측정 API/구간
- 입력/출력 native token 수, 문자 또는 UTF-8 byte 수, EOS/잘림 비율
- 실제 optimizer updates, 처리 예제/pass, target tokens, trainable params
- 학습 elapsed time/GPU session accounting과 모델 다운로드 시간의 구분

전체 생성 시간으로 나눈 tokens/s를 decode-only 속도라고 하지 않는다.
토크나이저가 다른 모델 간 tokens/s만으로 한국어 응답 속도를 단정하지 않는다.
출력 문자량/길이와 함께 해석한다.
정확도 평가를 위해 없는 토큰을 억지로 생성하거나 EOS를 막지 않는다.

학습용 같은 예제 수는 같은 FLOPs 또는 같은 학습 비용이 아니다.
모델별 총/언어/vision/LoRA parameter 수와 실제 시간을 보고한다.
모델명에 쓰인 2B/4B를 모두 똑같은 parameter 집계 방식이라고 가정하지 않는다.

문항 쌍에 대한 변화와 95% 신뢰구간을 계산한다.
VQA는 image/duplicate group, 텍스트는 가능한 source document/question group을 고려한
paired bootstrap을 사용하고 집계 단위와 반복 수를 명시한다.
seed 내 문항 불확실성과 seed 간 학습 변동을 별도로 보여준다.
다수 모델 중 최고 숫자 하나를 찾았다는 이유로 통계적 우월성을 단정하지 않는다.

======================================================================
9. 재개·장애·공간 관리
======================================================================

단계별 상태, immutable config, source snapshot, data/model identity,
선택/최종 checkpoint, 실제 명령, 소유 PID, GPU usage ledger를 보존한다.
정상 종료와 재개를 실제 artifact 기준으로 판단하고 파일 이름만 보고 성공 처리하지 않는다.

새 V6 CLI/wrapper는 plan/preflight/train/validate/select-seeds/evaluate/report 또는
동등한 단계별 실행 및 all/resume 동작을 제공한다.
성공 단계를 검증하여 건너뛰고, 다른 identity의 checkpoint를 이어 학습하지 않는다.
실행되지 않은 GPU 단계는 PENDING/BLOCKED로 남긴다.
dry-run이나 CPU 단위검사를 실제 GPU 학습 성공으로 표기하지 않는다.

시간 상한은 unlimited/null을 유지한다.
OOM·저장 공간·손상 checkpoint·접근 거부는 실제 원인으로 기록한다.
모델 캐시를 무한히 늘릴 수 있다고 가정하지 말고 다운로드 전에 필요 공간을 점검한다.
동일 base를 text/VQA용으로 중복 다운로드하지 않는다.
기존 원본, 기존 모델/학습 결과, optimizer/RNG를 공간 확보 명목으로 임의 삭제하지 않는다.
새로 만든 재다운로드 가능한 V6 임시 캐시는 명세를 남겨 정리할 수 있다.

한 모델의 gate/호환성/자원 부족은 다른 모델의 준비·학습·평가·보고를 막지 않게 한다.
외부 입력이 정말 필요한 경우에만 실제 오류, 필요한 최소 입력, 영향을 받는 셀을 모아
최종 사용자 할 일에 적는다. 이미 받은 데이터·API 키·매핑을 추측으로 다시 요청하지 않는다.


======================================================================
9A. 독립 학습 worker와 20분 예약 점검
======================================================================

목표는 학습을 계속 돌리면서 Codex의 대화 턴은 짧게 끝내는 것이다.
20분은 학습을 멈추는 주기가 아니라 상태를 확인하는 주기다.
GPU 학습은 worker가 계속 수행하고, 점검은 확인·제한된 복구·다음 단계 진행만 담당한다.

A. 먼저 현재 작업을 인계한다.
- 실행 중 학습이 있으면 repo/data/venv 절대경로, config/source hash,
  run ID, PID, process start time, host boot identity, GPU lock을 확인한다.
- PID 숫자만 같다고 같은 작업으로 간주하지 않는다.
- 정상 실행 중인 worker를 예약 구조로 옮긴다는 이유로 종료하지 않는다.
  먼저 read-only 감시 대상으로 등록하고, 다음 미시작 단계부터 새 supervisor를 사용한다.
- 기존 worker가 이미 자체 queue를 진행한다면 legacy queue owner로 기록한다.
  이 worker가 끝날 때까지 새 supervisor는 관찰만 하며 같은 queue의 작업을 시작하지 않는다.
  종료와 소유권 인계를 확인한 뒤 미시작 범위의 queue 소유자를 한 번만 변경한다.
- 실행 코드·환경 변경은 live worker와 분리된 snapshot 또는 worktree에서 한다.
  GPU lock과 run registry는 모든 worktree가 공유하는 private data root에 하나만 둔다.

B. 채팅과 독립된 실행을 구성한다.
- 실제 OS/WSL/service 환경을 확인해 사용자 권한의 service/process supervisor를 선택한다.
  Linux/WSL에서 사용 가능한 systemd user service, Windows 작업 스케줄러 등
  현재 환경에서 정상 지원되는 방식을 사용한다.
- 실행 중 채팅 tool session만 worker의 생명주기를 소유하게 하지 않는다.
  창이나 점검 턴이 종료돼도 worker가 유지되는지 짧은 시험 작업으로 검증한다.
- 새 구조에서는 단일 supervisor가 선언된 유한 queue의 전이·시작·재개를 소유한다.
  GPU worker는 할당받은 한 작업만 수행한다. timer/Codex는 공통 lock 아래 supervisor에
  점검/복구 요청을 보내며 직접 별도의 다음 GPU 작업을 시작하지 않는다.
  성공 단계는 검증해서 건너뛰고 V6 terminal 후 V7을 이어간다. 점수가 낮다고 계획을 늘리지 않는다.
- worker의 heartbeat/진행 파일은 해당 worker가, queue/복구 횟수는 supervisor가,
  점검 요약은 감독 경로가 소유한다. atomic write만으로 다중 writer 충돌이 해결됐다고 보지 않는다.
- checkpoint·log는 private data root에 저장하고 상태는 atomic write로 갱신한다.
- 사용자가 제거한 GPU 시간 상한을 서비스의 숨은 실행 제한으로 되살리지 않는다.
  유한 작업 완료/실제 오류로 종료하며, 정상 training wall time을 이유로 자동 중단하지 않는다.

C. 상태 계약을 만든다.
필수 상태 필드:
campaign_id, phase, cell_id, run_id, config/data/model/source hashes,
worker_pid, process_start_time, boot_identity, heartbeat_at, last_progress_at,
optimizer_step, total_updates, last_complete_checkpoint, exit_code,
recovery_attempts, pending/terminal cells, scheduler_identity, updated_at.

heartbeat는 optimizer step과 별개로 갱신한다.
컴파일·validation·checkpoint 저장 중에는 step이 한동안 증가하지 않을 수 있다.
health record와 last-progress를 분리하고 정상적인 느린 단계를 hang으로 오판하지 않는다.
전체 private log 대신 요약 상태와 필요한 오류 부분만 예약에 제공한다.

D. 20분 예약 등록은 실제 지원 기능으로 확인한다.
1) 사용 중인 Codex/데스크톱 앱의 기존 채팅 후속 예약이 분 단위를 지원하고,
   실제 연결 도구·계정에서 20분을 수락하면 이 작업 채팅의 local 프로젝트에 하나만 등록한다.
   timezone은 Asia/Seoul이다. 매번 다른 worktree/데이터 루트를 새로 만들지 않는다.
2) 네이티브 예약이 20분을 지원하지 않으면 그 제한을 그대로 따른다.
   학습 PC의 OS timer로 20분마다 짧은 감독 스크립트를 실행해 상태 확인을 유지한다.
   Codex 판단이 필요한 예약은 지원되는 간격에서 별도로 구성하고 실제 간격을 명시한다.
   1시간 제한을 3개의 엇갈린 예약으로 우회하지 않는다.
3) 여기 ChatGPT 웹 대화의 예약 도구는 최소 1시간이므로, 이 문서가 작성됐다는 사실만으로
   20분 예약이 등록됐다고 해석하지 않는다. 학습 PC의 Codex에서 실제 등록을 검증해야 한다.
4) Cloud 채팅의 GitHub 접근을 로컬 GPU/process 접근과 혼동하지 않는다.
   실제 학습 호스트의 상태·파일에 접근 가능한 실행 환경을 연결한다.
5) 등록 결과의 task/service ID, 실제 간격, timezone, 실행 cwd, 다음 예정 시각,
   모델·추론 강도(지원되는 경우), 활성 상태와 첫 점검 결과를 기록한다.
   등록 실패나 수동 활성화가 필요한 경우 성공으로 보고하지 않는다.

OpenAI의 공식 문서는 기존 채팅의 분 단위 후속 예약을 설명하지만,
모든 앱·계정·연결 도구가 같은 최소 간격을 지원한다는 보장은 아니다.
로컬 파일을 쓰는 앱 예약은 컴퓨터와 앱이 실행 중이고 프로젝트 경로가 유지돼야 한다.
독립 worker 자체의 생명주기와 앱 예약의 실행 조건을 별도로 검증한다.
필요하면 작업 동안 기존 절전 방지 설정을 활용하고, 종료 시 원상복구할 변경 내역을 남긴다.

E. 매번 실행하는 단일 점검 절차:
1) supervisor lock을 non-blocking으로 잡는다. 이미 다른 점검자가 있으면 즉시 끝낸다.
2) state/manifest/PID/start time/boot identity와 실제 worker를 대조한다.
3) worker가 정상이라면 요약 상태만 갱신하고 종료한다.
   다음 점검까지 sleep하거나 같은 턴에서 로그를 반복 조회하지 않는다.
4) 한 단계가 정상 완료됐다면 supervisor가 같은 lock과 상태 전이 안에서 artifact를 확인하고
   다음 선언 단계 하나를 시작한다. timer/Codex는 이 전이를 요청만 한다.
   legacy queue owner가 진행 중이면 별도로 같은 다음 작업을 시작하지 않는다.
5) 실제 종료/실패라면 마지막 완전 checkpoint와 identity를 확인한다.
   허용된 동일 실행 재개만 수행한다. 손상·미완성 checkpoint를 이어붙이지 않는다.
6) 오류 복구 횟수는 run 상태에 누적한다. 예약 호출마다 0으로 초기화하지 않는다.
   기존 모델·단계별 최초 시도 이후 최대 2회 기술 복구 규칙을 유지한다.
7) heartbeat가 한 번 늦거나 GPU 활용률이 낮다는 이유만으로 프로세스를 kill하지 않는다.
   진행 단계·로그·process 상태를 함께 확인한다. 강제 종료가 필요할 정도의 실제 hang이면
   이유와 보존 checkpoint를 기록하고 해당 작업에만 제한적으로 적용한다.
8) 코드 수정이 필요하면 실행 중인 다른 GPU 작업을 건드리지 않고 수정·관련 검사 후
   남은 복구 범위에서 새 source identity로 처리한다. 기존 성공 결과는 다시 실행하지 않는다.
9) 외부 접근 차단은 해당 셀에 기록하고 가능한 다른 셀을 계속한다.
10) 모든 V6/V7 셀이 terminal이고 보고서/CI가 확인되면 최종 보고 후
    이 campaign이 만든 예약·timer만 비활성화하고 중지 성공을 확인한다.

F. 알림·실행 비용:
- 정상 heartbeat만 반복되면 매번 긴 채팅 보고를 만들지 않는다.
- 주요 단계 완료, 실제 오류, 새 사용자 입력 필요, 최종 완료 때만 상세 보고한다.
- 매 20분마다 전체 테스트·원본 압축 감사·모델 hash 전량 재계산·재설치를 반복하지 않는다.
- 규칙으로 판정 가능한 상태 수집은 가벼운 로컬 스크립트로 수행한다.
- 복잡한 해석과 코드 수정이 필요한 경우에만 Codex 판단을 사용한다.
- 불필요한 유료 API나 별도 gateway를 감시를 위한 새 필수 구성요소로 추가하지 않는다.

G. 최초 턴 종료 전에 확인할 것:
- worker가 실제 실행 중이거나 기존 worker를 정상 감독 대상으로 인계했다.
- 점검 script의 정상/완료/중단/중복 실행 분기를 의미 있는 작은 fixture로 검증했다.
- 하나의 수동 점검을 성공했고 예약/service의 실제 ID·다음 예정 시각을 확보했다.
- 짧은 launcher/시험 부모 프로세스가 종료된 뒤 작은 독립 시험 worker가 살아 있는지 확인했다.
  실제 채팅 턴 종료 후 생존은 첫 예약 점검에서 확인해 receipt에 추가한다.
  시험 작업의 성공만으로 기존 학습 worker도 독립됐다고 표시하지 않는다.
  현재 장시간 학습을 일부러 종료하는 방식으로 시험하지 않는다.
- GPU 실행이 이미 가능하면 시작한다. 외부 차단이면 가능한 준비와 다른 셀을 끝낸다.
- 최초 응답에는 현재 단계·worker 상태·실제 점검 간격·다음 예정 시각·차단만 간결히 보고한다.

예약에 저장할 점검 프롬프트:
“mediflow-medvlm의 고정된 V6/V7 manifest와 supervisor state를 읽어 한 번만 점검하라.
동일 worker가 정상 실행 중이면 상태만 기록하고 이 턴을 끝내라.
완료 단계의 artifact를 확인하고 아직 시작하지 않은 승인된 다음 단계만 실행하라.
실제 실패는 checkpoint identity와 누적 복구 횟수에 따라 제한적으로 복구하고,
형식·데이터·seed·평가 규약을 결과에 맞춰 바꾸지 말라.
한 GPU worker와 한 상태 변경자만 유지하라. 긴 sleep이나 반복 polling을 하지 말라.
중요한 변화나 실제 사용자 입력 필요 사항만 보고하고,
V6/V7 전체 terminal 및 최종 보고서 검증 후 이 작업의 예약을 중지하라.”

11. V7 — 71762와 형식 과제 비율을 비교하는 최소 4조건
======================================================================

V6의 다중 모델 비교를 먼저 완료한 뒤 별도 V7으로 진행한다.
V6가 부분 실패로 terminal이면 V7에 필요한 Qwen3-1.7B 경로와 동결 평가 protocol을 확인한다.
선행 조건이 없으면 V7은 BLOCKED_PREREQUISITE로 종료하고 무한 대기·재시도를 하지 않는다.
V6에 71762를 섞거나 완료한 v4/v5를 덮어쓰지 않는다.
V7은 한 모델에서 과제 구성에 따른 변화를 보는 제한된 후속 실험이다.
공식 방식의 random pairing을 임의의 확정 정답으로 수정하는 작업이 아니다.

11-1. 제공처 회신을 반영한 감사

사용자 제공 회신의 요지는 다음과 같다.
- 고정 question-to-answer 매핑 자료는 제공하지 않는다.
- 파일 일련번호는 연관성이 없으며, category 폴더/질환명/의도 태그로 범위를 맞춘다.
- 같은 범위의 답변을 무작위로 사용한다.
- 증강 원본 parent 식별자는 제공되지 않는다.
- AI 모델의 “1. 모델 소스코드” 안 make_train_data.py가 random JSONL을 생성한다고 안내했다.

기존 v4의 독립 구현이 위 범위와 맞는지 이미 있는 receipt와 표본으로 확인한다.
category·질환명·의도 누락, 잘못된 split, question/answer 역할 뒤바뀜,
같은 질문의 중복 노출, 답변 재사용 횟수·분포, intro/body/conclusion 손실 등을 검사한다.
고유 질문/고유 답변/고유 쌍 수와 각각의 중복 빈도를 보고한다.
v4의 유한 후보 pool 및 fixed hash/seed는 구현상 선택이므로 공식 코드와 완전히 같다고 하지 않는다.

공식 코드를 새로 쉽게 확보할 수 있다면 차이를 읽기 전용으로 비교할 수 있다.
다운로드가 안 된다는 이유로 파일 찾기를 무한 반복하거나 V6/V7 전체를 막지 않는다.
이메일 요지와 승인 범위를 provenance로 남기되 공개 보고에 개인 연락처·메일 전문을 넣지 않는다.
LLM·embedding 점수를 임상 검수나 원본 parent 복원의 근거로 승격하지 않는다.

11-2. 모델·학습 행렬

모델: Qwen/Qwen3-1.7B 하나.
Base revision/loader/LoRA 범위/정답 마스킹은 V6에서 검증한 동일 조건을 사용한다.
네 조건 모두 원본 Base에서 독립 시작한다. v4/v6 adapter에서 연속 학습하지 않는다.
seed=20261023, LR=2e-4, NF4, r8/alpha16/dropout0.05, effective batch16,
기존 예제 평균 loss, 1 pass, 최종 checkpoint, fresh-process reload를 적용한다.
기본 N=2,000이면 각 조건 125 optimizer updates다. 추가 모델·seed·epoch sweep은 하지 않는다.

P: 원천에 실제 질문–답변 대응이 있는 71875 한국어 자유서술 train.
   기존 v2 KO의 단답 1,300/서술 1,200 후보에서 단답 1,000+서술 1,000을 고정한다.
   “paired”는 원천 대응 및 parser 검사라는 뜻이며 임상 전문가 전수검수라는 뜻은 아니다.
R: 기존 v4의 71762 fixed-random train 4,000쌍에서 2,000쌍을 고정한다.
   v4에서 이미 정한 연결을 재사용한다. 더 그럴듯한 답으로 바꾸거나 매 epoch 재추첨하지 않는다.
M: 기존 v2 KO의 71875 MCQ train 후보에서 400개를 고정한다.
   prompt/정답 label 형식은 V6와 동일하게 한다. P1/R1에서 같은 M을 사용한다.

네 조건:
P0 = P 2,000
P1 = P0의 동일 core 1,600(단답800+서술800) + M 400
R0 = R 2,000
R1 = R0의 동일 core 1,600 + 같은 M 400

P0의 나머지 자유서술 400개와 R0의 나머지 자유서술 400개가
각 replay 조건의 MCQ 400개에 대응하는 대조 노출이다.
총 예제/pass/updates를 고정하고 학습 예산의 20%를 MCQ 과제로 배분하는 실험이다.
MCQ를 추가해 replay 조건만 더 많은 optimizer update를 수행하는 방식으로 바꾸지 않는다.

P0/P1 및 R0/R1의 공통 core ID·원문 hash가 같음을 확인한다.
R의 core는 관측 가능한 질환 분류·답변 길이 분포를 가능한 한 유지한다.
M의 문항·정답·노출 위치 규칙을 두 replay 조건에 동일하게 적용한다.
성적을 보고 N·20% 비율·데이터 순서·seed를 변경하지 않는다.

11-3. 데이터 보호와 사전 수량 조정

P/R/M 모두 기존 train partition에서만 선택한다.
V6/V7의 공통 validation/test와 추가 외부 평가분까지 대상으로
기존 exact/near/semantic·번역 유사 후보 감사의 커버리지를 확인한다.
v4의 보호셋이 V6 공통 dev 전체를 포함했다고 가정하지 않는다.
부족한 경계 검사만 추가하고 원본 ZIP/HWP 전체 감사는 반복하지 않는다.

native train context=2048의 input+target, 전체 정답 보존, 마스킹을 검사한다.
질문이나 답변을 잘라 길이를 맞추지 않는다.
71762 원본 parent는 계속 unknown이며 관측 가능한 내용 그룹으로 보수적으로 보호한다.
환자·증강 lineage 독립성이나 개별 답변의 임상 정답성을 보장한다고 쓰지 않는다.

보호/길이 검사 후 기본 수량이 부족하면 모델 성능을 보기 전에만 공통 N을 축소한다.
모든 조건에 같은 N을 사용하고 20% replay와 batch16을 유지한다.
허용 후보 수를 n_short, n_long, n_R, n_MCQ라 하면:
N = 80 * floor(min(2000, 2*n_short, 2*n_long, n_R, 5*n_MCQ) / 80).
P0는 short/long 각 N/2, P1은 각 0.4N과 M 0.2N,
R0는 N, R1은 같은 R core 0.8N과 M 0.2N이다.
사전 최소 N은 800이다. 이에 못 미치면 V7만 데이터 부족 상태로 끝내고
V6 완료와 보고를 유지한다. test 결과를 보고 수량을 조정하지 않는다.

11-4. token/style 차이와 해석 범위

다음 값을 조건별로 기록한다.
- 실제 input/target token 총합, 평균/중앙값/p90, 정답 길이와 답변 section.
- source·task 비율, R의 질환 분류, 고유 질문/답변 수, 답변 재사용 빈도.
- 예제/update/pass 수, 최종 checkpoint, loss weighting과 같은 core의 일치 여부.

같은 예제 수가 같은 target-token 수라는 뜻은 아니다.
특히 M은 짧은 정답 label이므로 replay 조건의 token 총량은 달라질 수 있다.
target 길이를 맞추려고 정답을 삭제·요약하거나 clinical label을 새로 만들어 넣지 않는다.
현재 예제 평균 목적함수를 유지하고 “전체 token-matched”라고 주장하지 않는다.

가능한 해석:
- P0에서도 형식 유지가 나빠지면, 고정 Q/A 대응 부재만이 유일한 원인이라는 설명은 약해진다.
- P1/R1이 각각 좋아지면, 이 예제 예산에서 MCQ 과제에 20%를 배분한 처방이 도움이 된 것이다.
- R0와 P0의 차이에는 source 내용·문체·길이·질환 분포 차이가 남아 있다.
- P1−P0, R1−R0 및 두 변화량의 차이를 보고할 수 있지만,
  random pairing 하나의 순수 인과 효과 또는 형식만의 순수 효과로 표현하지 않는다.
- 한 seed의 네 조건에서 나온 결과를 모든 모델·데이터에 일반화하지 않는다.

11-5. 평가와 종료

V6에서 동결한 Qwen3-1.7B 평가 protocol을 그대로 사용한다.
V7 때문에 출력 상한·prompt·parser·scorer를 다시 고르지 않는다.
Base와 P0/P1/R0/R1을 같은 validation/test 문항과 예정 전체 분모로 비교한다.
Base 또는 참고 MIX 예측은 identity가 실제 일치할 때만 재사용한다.
기존 v4 4,000표본 학습은 R0의 2,000표본 학습을 대신할 수 없다.

주 지표:
- 한국어 MCQ의 valid-format rate와 strict all-row accuracy를 각각 보고.
- KorMedMCQA와 71875 MCQ를 source별로 분리.
- 영어 PubMedQA는 별도 전이/유지 지표로 보고.
  replay M이 한국어 MCQ이므로 영어 yes/no/maybe까지 같은 훈련을 받았다고 쓰지 않는다.
- correct/incorrect와 valid/invalid 전환, answered accuracy, 길이·잘림·실패.
- 검증된 V6 likelihood scorer가 있으면 보조 결과로 함께 제시.
- 자유서술 EM/F1은 별도이며 71762 random 참조와의 F1은 임상 정답률로 사용하지 않는다.

네 조건을 모두 보고한다. 최종 test 점수로 후속 모델/seed/epoch를 추가하지 않는다.
paired/group bootstrap 구간은 문항 불확실성이고, 한 training seed의 변동을 대신하지 않는다.
P0/P1/R0/R1의 data와 hyperparameter가 동결되기 전에는 새 test 추론을 실행하지 않는다.

71762 고정 표본 16~32쌍의 질문–답변 정합성 검토표를 private로 준비할 수 있다.
사람이 검토하지 않았다면 0건/미검수이며 자동 실험을 멈추는 선행 조건은 아니다.

별도 산출물:
- reports/public_summary/v7/의 한국어 결과/설계/한계, 조건 비교 CSV/JSON/그림.
- private v7 manifests, freezes, run/checkpoint/예측/검토표.
- 재현 명령, 원본 v4/v5 및 V6 보존 확인, INDEX/HANDOFF/WORKLOG 갱신.
- 네 조건 모두 성공 또는 구체적 terminal 사유, 검증된 fresh reload와 실제 CI.
V7은 새 본학습 최대 4조건이다. V6의 최대 18조건과 따로 집계한다.

12. 향후 Jetson Orin Nano 배포 검증 — 지금은 준비만
======================================================================

학습 장비를 바꾼다는 이유로 의료 SFT를 다시 수행할 필요는 없다.
현재 데스크톱에서 만든 base revision+adapter를 보존하고,
향후 실제 배포 artifact와 Jetson runtime을 별도 검증한다.

현재는 Jetson에 접속하지 않는다. IP/계정/장치 사양을 추정하지 않는다.
과거 다른 프로젝트의 Orin NX 16GB와 이번 Orin Nano를 혼동하지 않는다.
Jetson 학습·전송·재플래싱·JetPack 업데이트·실제 벤치마크는 실행하지 않는다.
대신 읽기 전용 장치 조사 항목, 변환 manifest, 평가 runner/계획을 준비한다.

향후 실제 장치에서 먼저 확인할 항목:
- Orin Nano 정확한 모듈 및 RAM 4GB/8GB, Developer Kit/Super 여부.
- JetPack/L4T/CUDA/TensorRT, OS와 aarch64 지원, 저장장치/남은 공간.
- nvpmodel, 전원·냉각, clocks와 thermal 상태.
- 같은 장치에서 실행할 UI·카메라·음성 모듈의 메모리 사용.
Super라는 이름이 RAM 증가를 뜻한다고 가정하지 않는다.
Jetson은 CPU/GPU가 물리 DRAM을 공유하므로 GPU 전용 VRAM처럼 전량 사용할 수 없다.

배포 후보는 데스크톱 검증 결과와 실제 backend 지원을 기준으로 좁힌다.
텍스트/VLM 모두를 한 번에 전체 학습 행렬만큼 Jetson에 올릴 필요는 없다.
논문용 모델 간 장치 성능 비교가 목적이면 사전 선언한 실행 가능 후보들을 같은 장치에서 비교하고,
단순 제품 배포가 목적이면 최종 후보 위주로 충분한 회귀와 성능 시험을 한다.
어떤 범위를 실행했는지와 OOM/미지원 모델을 빠짐없이 표시한다.

변환·품질 확인 단계:
A. 원래 검증된 desktop base+LoRA의 예측을 기준으로 보존.
B. 선택 runtime이 adapter를 직접 지원하는지 확인.
   필요 시 정확한 원본 base에 LoRA를 병합하고 병합 후 회귀 검사.
C. 지원되는 GGUF/INT4 등으로 변환·양자화하고 별도 artifact SHA/config를 기록.
D. 최종 artifact를 Jetson runtime으로 실행해 품질과 자원 지표를 확인.

QLoRA의 bitsandbytes NF4와 GGUF Q4_K_M/AWQ INT4는 같은 파일 형식·연산이 아니다.
단순히 “4bit”라는 이름이 같다는 이유로 결과가 같다고 가정하지 않는다.
새로운 양자화 calibration은 train/dev에서만 구성하고 test를 사용하지 않는다.
TensorRT serialized engine을 x86 RTX에서 만들어 Jetson에 그대로 복사하면 된다고 가정하지 않는다.
실제 architecture·plugin·TensorRT/JetPack 지원 조합과 engine 호환 조건을 확인한다.

모델별 converter/runtime 지원을 따로 표로 만든다.
llama.cpp/GGUF, TensorRT-LLM, TensorRT Edge-LLM은 각각의 현재 지원표를 확인한다.
Qwen 한 모델의 성공을 Gemma/MedGemma/Phi/Smol 전체 지원으로 확대하지 않는다.
VLM은 tokenizer·chat template·vision encoder·projector·image preprocessing까지 검증한다.
텍스트 출력이 된다는 사실만으로 이미지 입력 경로도 작동한다고 판정하지 않는다.

품질 회귀 범위:
- 같은 artifact/precision의 장치 이동: 고정 대표 사례의 기능·형식·출력 회귀 및 task 점수 확인.
- 병합/양자화/다른 kernel·runtime/processor 변경: 사전 고정된 충분한 의료 평가분으로 재평가.
- 최종 배포 artifact는 가능하면 기존 전체 고정 benchmark를 평가하여 desktop 대비 변화와
  숫자·단위·부정·선택지·한국어·잘림·VQA OPEN/CLOSED의 회귀를 보고.
- 전체 평가가 자원상 불가능하면 사전 선언한 공통 subset과 실제 분모를 명시.
  전체 benchmark 또는 임상 검증을 마쳤다고 표현하지 않는다.
- 품질 차이를 보고 양자화 설정을 선택했다면 그 평가를 model-selection에 사용한 것으로 기록한다.
  최종 확인용 평가 역할과 섞지 않는다.
- 기존 공개 benchmark는 새 blind test가 아니다. bitwise 동일성만을 합격 조건으로 삼지 않는다.

장치 성능 시험:
- cold load/첫 요청과 warm 상태를 구분.
- batch/concurrency1, 고정 입력·출력 제한·context·이미지 해상도와 processor.
- TTFT, decode 속도/토큰 간 지연, 전체 응답 p50/p95, 실제 출력 token/문자 수.
- RAM/SWAP/peak/메모리 부족, context·이미지 조건별 변화.
- tegrastats 등 실제 장치 계측의 온도·전력 rail·주파수·throttling.
- rail 전력과 콘센트 전체 소비전력을 구분.
- 최초 안정성 계획으로 30~60분 고정 요청 반복과 UI/카메라 동시 실행을 준비.
  이는 프로젝트의 제안 시험 길이이며 GPU 누적 시간 상한이 아니다.
- 숫자 기준은 사용자가 실제 응답시간 요구를 정하거나 측정 전 명시한 목표로 평가한다.
  근거 없는 “Orin Nano에서 몇 tokens/s 가능”을 예상 확정값으로 쓰지 않는다.

현 단계 산출물은 docs/research/JETSON_DEPLOYMENT_VALIDATION_PLAN_KO.md 등 계획과
실제 지원 여부를 아직 확인하지 않은 칸이 구분된 compatibility manifest다.
장치 측정 상태는 USER_DEFERRED/NOT_RUN으로 남긴다.
향후 접속·실행 범위가 실제 승인되면 이 계획에서 이어간다.

13. Codex 모델·추론 강도 운영 정책
======================================================================

아래는 작업 난이도에 맞춘 권장 운영값이다. 실제 앱/계정에 제공되는 모델을 확인한다.
- 초기 전체 설계 검토, 여러 architecture의 LoRA/mask/resume 구현,
  원인 불명 실패 및 71762 결과 해석: GPT-6 Astra / Extra High(xhigh).
- 확정된 처방의 구현, 일상적 수정·검증: GPT-6.1 Sol / High.
- 정기 상태 확인과 승인된 다음 단계 진행: GPT-6.1 Sol / Medium.
- 순수 상태 수집/완료 판정은 먼저 규칙 기반 스크립트로 수행.
  명확한 요약만 맡기는 경우 GPT-6 Luna / High도 선택 가능.

하나의 구현 대화 모델을 고르면 Astra Extra High를 우선 권장한다.
반복 사용량과 속도를 함께 고려하면 Sol High를 기본으로 하고
어려운 설계·해석·실패 분석을 Astra Extra High로 분리할 수 있다.

Ultra는 독립적인 데이터·학습 코드·평가 감사 같은 병렬 작업에 사용할 수 있다.
한 GPU의 학습을 병렬로 여러 개 띄우거나 정기 점검을 계속 무겁게 수행하는 지시가 아니다.
GPU worker와 mutable state의 최종 소유자는 하나로 유지한다.

예약의 모델/추론 강도는 현재 UI 또는 공식 도구에서 지원되는 설정으로 저장한다.
프롬프트에 이름을 적었다는 사실만으로 모델이 자동 전환됐다고 주장하지 않는다.
실제 예약/실행 receipt에 선택된 모델·강도를 기록하고,
자동 승격이 지원되지 않으면 현재 모델로 허용 범위의 작업을 계속한 뒤 해당 한계를 보고한다.
외부 유료 API 호출이나 새 credential 발급을 모델 전환의 필수 단계로 만들지 않는다.

R2 첫 전달 지시 — 이 파일을 첨부한 기존 Codex 작업 대화에서 사용
======================================================================

이 파일 전체를 앞선 V6 지시서의 통합 수정본으로 적용해줘.
현재 실행 중인 학습이 있으면 멈추지 말고 먼저 상태와 identity를 확인해 감독 대상으로 인계해줘.
V6의 8개 고유 모델·10개 작업 셀은 유지하고, 완료 후 제11절의 V7 네 조건을 별도로 실행해줘.
71762는 제공처가 안내한 random 연결 방식이라는 사실을 반영하되,
개별 질문–답변의 임상 정합성이 검증된 것으로 취급하지 말아줘.
장시간 학습은 독립 worker로 실행하고 이 채팅 턴은 초기 설정·검증 후 끝내줘.
이 프로젝트에 실제 접근 가능한 환경에서 20분 점검을 등록해줘.
앱 예약이 20분을 지원하지 않으면 OS timer의 20분 점검을 구성하고,
Codex 예약의 실제 가능한 간격은 구분해서 보고해줘. 제한을 우회하지는 말아줘.
실제 task ID·다음 실행 시각·worker 상태를 확인하기 전에는 예약 완료라고 말하지 말아줘.
Jetson은 향후 배포 검증 계획만 준비하고 지금 접속하거나 실행하지 말아줘.
GPU 시간 상한 없이 선언된 유한 실험만 진행하고 완료 후 예약을 중지해줘.
